# 2026-11-12 종료 무음 750ms 및 동일 음성 비교

## 결론

사용자의 750ms 실시간 시험에서 “휴지 가져다줘, 아니 멈춰” 3회 중 2회는 한 발화로
유지됐고 두 번째는 나뉘었다. 같은 음성을 재생해 600/750/810/900ms를 비교했으며,
900ms만 세 번 모두 한 발화로 유지했다. 시작 비율 0.4 / 종료 무음 900ms를 유지한다.
600ms·750ms를 운영 기본값으로 채택하지 않는다. 추가로 이 시험을 위해 재녹음할 필요는 없다.

## 실제 노드 로그

- 원본: `recordings/vad_end750.QP39aD/session.log`와 WAV 7개.
- 실제 설정: `speech=4/10`, `end_silence=0.750s`, small/CPU/int8/ko, beam 5,
  빈 힌트, temperature `[0.0]`, publish_commands=false.
- 안내한 6개 발화가 7개로 분리됨. 규칙 정지 5건, robot_unknown 차단 2건,
  ERROR 0건, `[ROS] skipped` 7건.

| 시험 | 실제 전사 | 결과 |
| --- | --- | --- |
| 수정 문장 1회 | 휴지 가져다 줘 아니 멈춰 | 한 발화, stop |
| 수정 문장 2회 | 휴지 가져다 줘 / 아니 멈춰 | 두 발화, 앞부분 차단 후 별도 stop |
| 수정 문장 3회 | 휴지 가져다 줘. 많이 멈춰. | 한 발화, stop. “아니”의 전사 오류는 남음 |
| 일반 긴 문장 | 목마른데 마실 거 가져다 줘 | 한 발화, robot_unknown으로 LLM 전 차단 |
| 스톱 | 스톱 | 규칙 stop |
| 멈춰 | 멈춰 | 규칙 stop |

정지 결과가 나왔다는 사실과, 그 전에 별도 가져오기 요청이 생기지 않았다는 것은 다르다.
두 번째 앞부분은 이번에 상태 미수신으로 차단됐지만 실제 IDLE/발행 상태에서는 먼저
fetch로 처리될 가능성이 있다. 이번에 실제 fetch나 로봇 동작이 일어난 것은 아니다.

## 같은 음성의 재생 비교

이번 두 번째 문장의 002/003 파일은 앞선 600ms 시험과 달리 저장 구간이 정확히 맞닿는다.

- 002: 종료 20.550초 − 실제 PCM 길이 1.980초 = 시작 18.570초.
- 003: 종료 22.080초 − 실제 PCM 길이 1.530초 = 시작 20.550초.
- 30ms 프레임의 정수 인덱스로 002의 끝과 003의 시작이 같음을 검사했다.
- 따라서 두 PCM을 순서대로 연결했다. 문장 안의 쉼에 무음을 삽입하거나 삭제하지 않았다.

1회/3회는 원래 한 파일이며, 2회는 위의 연결된 PCM을 사용한다. 일반 긴 문장과
스톱/멈춰도 별도 그룹으로 비교했다. 실제 `pipeline.capture_utterances`의 프레임 분할
로직을 사용하고, 마이크 입출력만 파일 프레임 입력으로 대체했다. LLM/ROS는 사용하지 않았다.

재생의 제한:

- 그룹마다 VAD를 새로 시작하고 startup warmup은 0으로 설정했다. 원래 상시 스트림의
  이전 소음/음성 이력까지 복제하지 않는다.
- 원본의 끝에는 750ms 무음만 있으므로, 900ms 종료 판단을 완료할 수 있게 **각 그룹 맨 끝에만
  합성 0 PCM 300ms**를 덧붙였다. 이는 새로 관측한 주변 소음이 아니다.
- 중요한 문장 내부의 분리 구간은 원본 PCM을 그대로 유지했다. 원래 750ms에서 관측한
  수정 문장별 분할 패턴(1개/2개/1개)과 해당 전사 결과가 재생에서도 재현됐다.
- 일반 긴 문장과 단독 스톱은 원래 스트림과 새 VAD의 종료 경계에 30~60ms 차이가 있었다.
  따라서 재생 결과는 이번 음성의 설정 비교 근거이며, 전체 실시간 동작을 완벽히 재현하거나
  모든 말하기 속도와 쉼에서 900ms가 문장을 유지한다고 보장하는 시험은 아니다.

| 종료 무음 | 수정 문장 1회 조각 수 | 2회 조각 수 | 3회 조각 수 | 한 발화 유지 |
| --- | ---: | ---: | ---: | ---: |
| 600ms | 2 | 2 | 2 | 0/3 |
| 750ms | 1 | 2 | 1 | 2/3 |
| 810ms | 1 | 2 | 1 | 2/3 |
| 900ms | 1 | 1 | 1 | 3/3 |

프레임 길이가 30ms이므로 800ms를 지정하면 구현상 810ms로 올림된다.
600/810ms는 분할 수만 비교했다. 750/900ms는 분할 후 실제 Whisper와 정지 규칙까지 실행했다.

900ms에서 수정 문장 1·2회는 “휴지 가져다 줘 아니 멈춰”, 3회는 “휴지 가져다 줘. 많이 멈춰.”로
전사돼 모두 stop이었다. 단독 스톱/멈춰도 stop이었다. 일반 긴 문장은 한 발화로 유지됐고
정지 키워드는 없었다. “많이” 오전사는 900ms로 고쳐진 문제가 아니며 그대로 남는다.

이 비교는 음성 종료 판정/전사 시험이다. STT 측정 순서·워밍업을 통제한 속도 벤치마크나
종단 지연, LLM 분류 정확도, 실제 로봇 정지 완료 시험으로 해석하지 않는다.

  확정 설계의 정지 전용 오디오 감지 경로를 별도 검토한다. 아직 구현/검증 완료가 아니다.

시험용 750ms 프로세스를 종료하고, 다음 실행에서 `vad.end_silence_ms:=750`을 제거하면
기존 900ms가 적용된다. 새 터미널에서는 `cd ~/2026project`, `source voice_env.sh`로 준비한다.
같은 준비된 터미널의 노트북 dry-run 실행 명령:

```bash
ros2 run voice_command_pkg voice_command_node --ros-args \
  --params-file "$PWD/src/voice_command_pkg/config/voice_command.yaml" \
  -p publish_commands:=false
```

다른 준비된 노트북 터미널에서 실제 설정 조회:

```bash
ros2 param get /voice_command_node vad.start_speech_ratio
ros2 param get /voice_command_node vad.end_silence_ms
```

정상 값은 각각 0.4, 900이다. 이번 결정을 위해 같은 문장을 또 녹음할 필요는 없다.
