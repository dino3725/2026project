# 팔 목표 추종 진단 및 도착 확인 보완 — 2026-11-12

## 결과

상자를 치운 뒤 상향 진단 1회를 실행했다. 하위 제어기는 성공을 반환했지만, 어깨에
약 5.03° 오차가 남았다. 새 도착 확인 기능이 이를 검출하여 ERROR로 멈췄다.
자동 HOME·추가 하강·파지·그리퍼 동작·주행은 실행하지 않았다.

현재의 일부 위치 오차는 **명령한 관절 각도에 실제 관절이 도착하지 않는 현상**이다.
카메라 보정값을 더 조정하는 것만으로 이 각도 차이를 해결할 수 없다.
모터 내부 제어·부하·전원·마찰 등 물리 원인은 아직 확정하지 않았다.

사용자 요청으로 오늘 실험을 마쳤으며 하드웨어·MoveIt·카메라·vision·joy와
측정 제어기를 모두 종료했다. 종료 직전 진단 경로 1회 실행 후 ERROR 상태였다.
기본 자세·속도/가속 배율 0.10·그리퍼 값·모터 게인은 바꾸지 않았다.

## 추가 이동 전 확인

직전 높은 접근 자세를 유지한 채 10초 동안 173개 표본을 수집했다.

| 항목 | joint1 | 어깨 joint2 | 팔꿈치 joint3 | 손목 joint4 |
|---|---:|---:|---:|---:|
| 목표 대비 중앙값 오차(도) | -0.123 | +1.574 | +2.417 | +0.354 |
| 표본 표준편차(도) | 0.015 | 0.043 | 0.024 | 0.026 |

오차는 잠깐의 정착 지연이 아니라 정지 상태에서도 유지됐다.
`controller_state.feedback`와 `/joint_states` 차이는 최대 1엔코더 틱이었다.
공식 2.2.1 드라이버는 Present Position을 읽고 Goal Position과 같은 4096틱/회전
변환을 사용한다. 1틱은 약 0.08789°로, 수 도의 오차를 단순 반올림으로 설명할 수 없다.

기존 보정 촬영 30개 자세의 저장된 목표와 관절값도 대조했다. 각 관절 오차 중앙값은
[-0.038, +0.439, +0.472, +0.176]°, 최대 절댓값은 [0.158, 1.688, 1.361, 0.354]°였다.
촬영 당시 관절값은 독립 실측이 아니며, 일부는 촬영 시각에 가장 가까운 저장값이다.
이 자료를 하나의 고정 관절 보정값으로 적용하지 않았다.

## 구현한 도착 확인

`control_pkg/arm_arrival.py`에 ROS와 무관한 관절 오차·경로 끝점 검증 함수를 추가했다.
`ControlNode`는 액션 성공 후 다음 조건을 별도로 확인한다.

- 목표 대비 모든 관절의 차이가 **1° 이내**.
- 실제 상태가 완료 후 새로 수신됐고, 수신 시각과 메시지 시각 모두 **0.5초 이내**.
- 조건을 **0.3초 동안** 유지. 검사는 최대 **2초** 동안 수행한다.
- Cartesian 이동은 실제 TF의 위치도 기존 위치 허용값 **10mm 이내**인지 확인한다.
- 누락·NaN·오래된 상태·실행 경로 끝점 누락은 통과시키지 않는다.
- 기다리는 중에도 기존 operation_id/취소 구조를 사용한다.

적용 위치: HOME/인식/CARGO 등 관절 이동, MoveIt Cartesian 이동, 실행된 RETREAT,
단발 접근/진단 도구. 도착 실패는 `ArmArrivalUnverified`로 전달되어 하강·집게 닫기·
자동 HOME으로 이어지지 않는다. 이 기준은 진행 여부를 막는 소프트웨어 기준이며,
실제 손끝의 절대 위치 정확도나 성공적인 파지를 인증하지 않는다.

새 검사 때문에 이전에 성공으로 처리하던 자세가 ERROR로 바뀔 수 있다.
허용치를 늘려 통과시키는 대신 원래의 추종 오차를 먼저 해결해야 한다.

## 상향 진단 1회

사용자가 콜라·상자를 팔 아래에서 치웠다고 확인했다.
이전 경로의 최종 관절 목표에서 어깨만 -6° 변경하고 다른 관절 목표는 유지했다.
전체 경로에서는 실제 시작 관절값에서 목표값으로 보간되므로 다른 관절도 기존 오차를
줄이는 방향으로 조금 움직일 수 있다. '다른 관절 목표 유지'가 모든 관절의 물리적
완전 고정을 뜻하지는 않는다.

- 목표 EE: base_link 약 (261.9, 22.8, 328.3)mm.
- 기존 가상 충돌 영역 및 카메라 부착 형상 유지, 40개 보간 지점 검증.
- 처음 생성된 0.727초 경로는 실행하지 않았다. 진단 경로를 기존 관절 이동 시간에 맞춰
  4초 이상으로 시간 확장하고 속도/가속도 배열도 비례 조정한 새 계획만 실행했다.
  MoveIt 요청 배율은 0.10을 유지했다.
- 실행한 경로 SHA256:
  `384020ab1b49ea10adfa2da7a7bc6d7547486ce745ba6ae0a05affcc08ce9ace`.
- 하드웨어는 재시작하지 않았다. 완료된 이전 측정 제어기만 SIGTERM으로 종료하고 새
  도착 검사 버전을 시작했다. 시작 시 추가 Y 확인은 사용자 요청대로 생략했다.
- 하위 액션은 SUCCEEDED. 새 도착 검사는 어깨 약 5.03° 오차를 검출하여 ERROR.

5초 87개 표본으로 확인했으며 각도 변화의 표준편차는 0.01~0.04°였다.

## 하드웨어 종료 동작 정정

공식 2.2.1 `OpenCR::~OpenCR()`는 종료 시 특정 관절 위치를 쓰고 집게를 초기화한 뒤
3초 대기 후 토크를 해제한다. 설치된 라이브러리의 해당 함수도 디스어셈블하여
같은 호출과 위치 상수가 들어 있음을 확인했다. 즉, 상위 프로그램이 HOME을 보내지
않더라도 공급 드라이버 종료 과정에서 팔/집게 명령이 발생할 수 있다.

앞선 '종료 시 새 동작 없음' 설명은 상위 제어기에 한정되는 표현이었으므로 정정했다.
`EATED_TERMINALS.md`, 종료 기록, `eateded` 실행 안내에 이를 반영했다.
공급 드라이버 자체는 이번에 수정하거나 재시작하지 않았다.

참조: [ROBOTIS 2.2.1 OpenCR 소스](https://raw.githubusercontent.com/ROBOTIS-GIT/turtlebot3_manipulation/2.2.1/turtlebot3_manipulation_hardware/src/opencr.cpp),
[공식 ROS2 position 명령 인터페이스 설명](https://control.ros.org/humble/doc/ros2_controllers/joint_trajectory_controller/doc/userdoc.html).
현재 position 인터페이스에서 `open_loop_control`만 false로 바꾼다고 별도의 PID 힘
보정기가 생기는 것은 아니다. 이 설정을 추측으로 바꾸지 않았다.

## 남은 작업

1. 모터별 운전 모드·내부 위치 게인·전류/부하/온도·전원 상태를 충돌 없는 독립 절차로 확인.
2. 동일한 안전 자세에서 명령 방향·부하에 따른 추종 오차를 비교하여 원인을 구분.
3. 추종 오차를 해결한 뒤 손끝 기준과 카메라/팔 모델의 남은 절대 오차를 다시 검증.
4. 그 후에만 물체를 돌려놓고 높은 접근 → 하강 → 파지 순서로 진행.

현재 관절이나 카메라에 고정 오프셋을 추가하지 않았다. 파지 실험은 재개하지 않는다.
